# Chapter 1: Introduction

## 1.1 Background and Motivation

Large language models are increasingly used as components of software agents
that can retrieve information, call tools, retain memory, and carry out
multi-step tasks. Unlike a single-turn language-model application, an agent
typically invokes the model repeatedly. Before each invocation, the surrounding
software constructs an input from several sources: system instructions, the
current user request, conversation history, retrieved passages, stored memory,
tool descriptions, tool outputs, and intermediate execution traces. ReAct, for
example, interleaves model-generated reasoning and actions with observations
returned by an external environment [@yao2022react]. Retrieval-augmented
generation adds documents selected from an external corpus
[@lewis2020rag], while memory-oriented architectures retrieve previous
observations or reflections to support longer-lived behavior
[@park2023generative; @shinn2023reflexion]. These mechanisms make an agent more
capable, but they also make the model input a dynamic software artifact rather
than a prompt written entirely by the user.

This thesis calls that artifact *automatically constructed context*. More
precisely, the term refers to the complete model-visible input assembled by an
agent runtime for a particular model invocation. The content may have been
written by a developer, entered by a user, generated by an earlier model call,
retrieved from storage, or returned by a tool. What matters is that the agent
software selects, transforms, orders, and transmits it to the model. This
invocation-level perspective is important because neither the user-facing
conversation nor an application log necessarily reveals everything that the
model received.

A larger context window does not remove the need to manage this constructed
input. Long-context studies have shown that nominal capacity and effective use
are different properties. Liu et al. found that model performance could change
substantially with the position of relevant information and was often weaker
when the information appeared in the middle of a long input
[@liu2024lost]. RULER similarly showed that models that performed well on simple
needle-in-a-haystack retrieval could degrade as context length and task
complexity increased [@hsieh2024ruler]. These studies do not examine agent
context bloat directly, but they establish a key motivation for this thesis:
placing more text inside the context window does not guarantee that the text is
useful or that the model will use it robustly.

Agent workflows create several concrete routes by which unnecessary context
can accumulate. A retriever may return overlapping passages or documents with
low query relevance. A memory component may preserve stale facts or replay the
same conversation details across turns. A tool may return verbose structured
data when the next model call needs only one field. A multi-step loop may append
the same tool observation, framework instruction, or intermediate trace more
than once. Individually, such additions can look harmless. Across repeated
invocations, however, they can increase input tokens, latency, and cost, while
making it harder for developers to understand which source dominates the
model's input.

The problem is therefore not simply that agent contexts can be long. A long
context may be necessary when a task depends on many distinct facts. The
problem is *context bloat*: avoidable model-visible content that is duplicated,
irrelevant to the current task, stale, or more verbose than the task requires.
This distinction makes context bloat a provenance and measurement problem as
well as a compression problem. Before content can be removed safely, a
developer needs to know what entered the context, where it came from, how much
it contributed, and why it was classified as unnecessary.

General agent observability provides part of this foundation. Agent tracing can
record model calls, tool calls, state changes, and execution paths, and recent
AgentOps work has argued for observability across the lifecycle of LLM agents
[@dong2024agentops]. Yet a conventional execution trace does not by itself
provide a source-level account of the exact text visible to the model, nor does
it quantify redundancy and bloat within that text. This thesis narrows the
observability problem to the model-call boundary and uses runtime auditing to
turn automatically constructed context into an analyzable and reproducible
artifact.

## 1.2 Research Problem and Objectives

The central research problem is how to detect, localize, measure, and mitigate
context bloat in LLM-based agents. The challenge has four parts. First, bloat is
distributed across heterogeneous sources. The same invocation can contain
retrieved passages, memory entries, tool results, framework instructions, and
model-generated traces, each with different structure and provenance. Second,
bloat is relational. A segment may be useful in one task but irrelevant in
another, and a passage may be acceptable once but redundant when repeated.
Third, raw token counts reveal size but not necessity. Measuring bloat requires
distinguishing total context from the part judged avoidable under an explicit
criterion. Fourth, mitigation introduces a utility risk: reducing tokens is not
valuable if the removed content causes the agent to fail.

This thesis addresses the problem through a runtime auditing approach. The
auditor captures the client-side serialized request immediately before each
model invocation, divides its model-visible content into ordered segments, and
labels each segment by source. It records character and token counts, raw and
normalized content hashes, provider-request hashes, and invocation-level
metrics. Injected labels, detected labels, human annotations, and
counterfactual outcomes occupy separate fields so that one evidence type cannot
silently substitute for another.
Because the trace preserves the relationship between a flag and its originating
segment, a detected problem can be localized to retrieval, memory, tool output,
framework content, or another source rather than reported only as an aggregate
token increase.

Study A operationalizes context bloat using patterns that can be introduced and
verified reproducibly: exact duplicates, near duplicates, low-query-relevance
content, verbose tool output, and combinations across sources. These injected
labels check implementation consistency but are not an independent gold
standard. Study B therefore constructs contexts without bloat metadata and
uses blind human judgements as its reference. Study C adds a behavioral
criterion by testing whether removing a candidate preserves task utility.

The empirical evaluation separates three kinds of evidence. Study A is a
controlled perturbation benchmark. It determines whether the trace, labeling,
metric, and reporting pipeline behaves consistently when the injected pattern
is known. Study B uses natural agent traces and independent human annotations
to test whether the heuristic signals transfer beyond the rules that generated
the controlled fixtures. Study C then removes individual candidate segments
and compares a provenance-aware mitigation with an equal-budget prompt
compression baseline. This separation prevents an injected label from being
used as if it were an independent reference standard.

The scope is deliberately narrower than a general-purpose safety or
optimization system. The thesis does not attempt to identify every form of
harmful prompt content, protect against all prompt-injection attacks, maximize
model accuracy, or design an optimal compression algorithm. Runtime tracing and
provenance are the research instruments; context bloat is the main phenomenon.
Mitigation is evaluated as a bounded case study after detection and measurement
have been established.

## 1.3 Research Questions

The investigation is organized around four research questions.

**RQ1: How accurately can provenance-aware heuristic signals detect and
localize independently annotated context bloat in natural LLM-agent traces?**

RQ1 concerns both classification and location. Each heuristic signal must map
to a specific model-visible segment. Its primary reference is the adjudicated
judgement of two human annotators who do not see framework identity, provenance
labels, detector output, or model answer. Study A remains a software
consistency check; external accuracy is estimated only from Study B.

**RQ2: To what extent do automated context-bloat measures agree with
independent human judgements and counterfactual removability?**

RQ2 examines whether the detected token ratio is calibrated to a
human-reference bloat ratio and whether a segment judged removable can in fact
be deleted without lowering task performance. Agreement is reported using
correlation, absolute error, calibration, and Bland-Altman bias. The
counterfactual test is deliberately stricter than a label: deletion must
preserve performance in both independent provider replicates.

**RQ3: What bloat sources and patterns are observed across retrieval, memory,
and tool workflows under controlled and naturalistic conditions?**

RQ3 keeps injected and observed patterns separate. The controlled study shows
how predefined perturbations appear in the metrics. The natural-trace study
reports source-specific human-reference ratios, confidence intervals, and
effect sizes. A source ranking is therefore scoped to the sampled tasks and
execution design rather than presented as a universal property of agents.

**RQ4: What token and cost savings, and what task-performance trade-offs,
arise from provenance-aware mitigation compared with prompt compression?**

RQ4 compares unmodified requests, provenance-aware mitigation, and
LLMLingua-2 under the same retained-token budget. It reports token, cost,
latency, and task-success differences separately. A -5 percentage-point
non-inferiority margin means that the intervention may add at most one failure
per twenty tasks; -2 and -10 percentage-point margins are included as
sensitivity analyses. Token reduction is not interpreted as utility-preserving
mitigation unless the human-scored task outcome supports that claim.

## 1.4 Contributions and Thesis Structure

The thesis is designed to make four linked contributions.

First, it presents an operational taxonomy and an evidence model for context
bloat. The taxonomy distinguishes exact and near duplication, low-relevance or
stale material, verbose tool output, and cross-source accumulation. The
evidence model further distinguishes an injected perturbation, a heuristic
indicator, a human reference label, and a counterfactually removable segment.
These terms are not interchangeable.

Second, it defines a provenance-aware model of the client-side serialized
request. The model represents messages, additional system instructions, tool
definitions, generation parameters, and response formats for a particular
invocation. Source-labeled segments support token attribution and normalized
content identity, while paired framework-capture and provider-payload hashes
make boundary mismatches explicit. This is a claim about the request sent by
the client, not unobservable transformations inside the provider.

Third, it implements the model as a Python runtime auditing toolkit and a
reproducible validation pipeline. The toolkit captures requests from LangChain
and Custom ReAct execution paths, writes schema-versioned JSONL traces, rejects
injected labels in external-validation runs, exports condition-blind annotation
packages, enforces a shared provider-call budget, and associates every run with
an immutable manifest and output hashes.

Fourth, it combines a controlled perturbation benchmark with an independently
annotated natural-trace study and a utility-aware mitigation study. Study A
contains 1,596 invocations and 1,188 completed task runs. Its perfect
rule-matching scores demonstrate internal consistency only. The original
source-aware mitigation reduced context tokens by 48.85% on average (95% CI
[42.67%, 55.31%]), but task success changed by -6.11 percentage points (95% CI
[-12.22, -0.56]). This is evidence of performance-degradation risk, not merely
an inconclusive positive result. Studies B and C were introduced specifically
to test the detector against independent labels and to compare mitigation with
a prompt-compression baseline. Their numerical results are inserted only after
the frozen held-out runs and adjudication are complete.

The remainder of the thesis is organized as follows. Chapter 2 reviews agent
context construction, long-context limitations, context management,
observability, and related mitigation work. Chapter 3 defines the bloat and
evidence models, metrics, and auditing architecture. Chapter 4 presents Studies
A, B, and C, including annotation, counterfactual, and statistical procedures.
Chapter 5 reports controlled and independent evidence for RQ1-RQ3. Chapter 6
evaluates mitigation, answers RQ4, and discusses engineering implications and
limitations. Chapter 7 consolidates the answers within their stated evidence
boundaries.
